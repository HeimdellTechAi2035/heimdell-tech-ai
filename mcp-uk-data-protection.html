MCP Servers and UK Data Protection

Permissions have to be designed on purpose. This is not legal advice.

Quick answer: An MCP server lets an assistant use your tools. It also creates a new path to personal and business data, so the permissions have to be designed on purpose. The assistant should see only the tools you choose, write actions should need a person where the change matters, and you should keep a log. This page explains the idea in line with published ICO guidance. It is not legal advice and it is not a verdict on any named supplier.

What an MCP server is doing

The Model Context Protocol specification gives applications a standard way to share context with a language model, expose tools, and build workflows. It uses JSON-RPC between a host (the application that holds the model), a client inside that host, and servers that provide capabilities.

Servers can offer three kinds of thing. Tools are functions the model can call, such as an API request or a database query. Resources are data for context, such as a file, a schema or an application record, each identified by a URI. Prompts are reusable templates. Clients discover them with list methods and then either read a resource or call a tool. The architecture overview uses a database server as the worked example: tools to query it, a resource for the schema, and a prompt that shows how to ask.

For a small UK firm, the same shape might be a bookings diary, a customer list in a CRM, or accounting records in software such as Xero. Heimdell Tech Ai does not publish a named connector for any of those products on this page. The point is the pattern. Whatever you connect becomes reachable by the assistant, to the extent the tool returns it.

The building service is MCP servers. This guide is the data-protection angle that page does not cover.

What a typical setup can and cannot see

MCP does not, by itself, grant a model access to every file and every inbox. The server exposes a list. If the only tool is “next free appointment”, the model can ask for that and receive the answer the tool is written to return. It does not receive the rest of the diary unless another tool, or a careless response, includes it.

That limit is easy to lose in practice:

  • A “search customers” tool that returns every field, including notes and payment references, is a wide window even if you only wanted a name.
  • A resource that points at a whole export, rather than one record, gives the model the export.
  • A tool description is not a safety control. The specification’s security section says tool descriptions should be treated as untrusted unless they come from a trusted server, because tools are arbitrary code execution from the host’s point of view.
  • Two transports behave differently for credentials. The authorisation specification says authorisation is optional. When HTTP is protected, it describes OAuth 2.1, with the MCP server as a resource server. For a local stdio transport, it says implementations should not follow that HTTP flow and should take credentials from the environment instead. A token left in a shared config is still a key.

So the honest answer to “what can it see?” is: whatever you put behind a tool or a resource, in the shape your code returns, for as long as the caller’s token or local process is allowed to call it.

Least privilege, approval and logging

The authorisation specification says that when a server tells a client which scopes are required, it should follow the principle of least privilege so the client does not ask for more access than the operation needs. Scopes are a protocol tool. They are not a substitute for deciding, in the business, which operation should exist.

The specification also says it cannot enforce its own safety principles. It asks implementers to obtain explicit user consent before a tool is invoked, and to make clear what the tool does. Hosts must obtain consent before exposing user data to servers, and must not pass resource data elsewhere without consent. Those are “should” and “must” lines in the specification for people building hosts and servers. They do not configure themselves on a small-business laptop.

A practical reading for a firm connecting its own systems:

  • Least privilege. One tool, one job, the smallest fields that job needs. A read of tomorrow’s free slots is not a reason to return customer medical or payment notes.
  • A person for write actions. Creating a booking, raising an invoice, changing a price or emailing a customer changes someone else’s position. Start with those calls requiring a person to confirm. The protocol will not insert that confirmation for you.
  • A log. Record which tool was called, when, and whether it was a read or a write. You need that to answer a customer, and to spot a tool that is being used for something you did not intend. The ICO’s security principle expects appropriate technical and organisational measures. A log is one organisational measure. It is not the whole of it.

Controllers, processors, and what to tell people

The ICO’s guide to the data protection principles sets out seven principles in Article 5 of the UK GDPR. Personal data must be processed lawfully, fairly and transparently; for specified purposes; and only as far as necessary (data minimisation). It must be accurate, kept no longer than needed, and secured. The controller must be able to demonstrate this. The ICO says infringements of the basic principles can attract the higher tier of fines, up to £17.5 million or 4% of worldwide annual turnover, whichever is higher. That is a reason to design the connection carefully. It is not a prediction about any particular MCP project.

The ICO’s explanation of controllers and processors is the other half. A controller decides the purposes and means of the processing. A processor processes personal data on the controller’s behalf. A processor should follow the controller’s documented instructions. If it goes beyond those instructions and decides purposes and means itself, it becomes a controller for that processing.

Applied carefully, and only as a principle: if your firm decides to let an assistant read customer bookings so staff can answer enquiries, you are likely to be a controller for that use. A software company that only hosts the tool and follows your instructions may be a processor, in which case the ICO says you need a binding contract with the compulsory Article 28 terms, and you remain responsible for the processing, including what the processor does. A model provider that uses the same data for its own purposes may not be “just a processor”. This page cannot classify a named vendor. Read the contract, and take advice before production data is connected.

Transparency means people are told, in plain language, who you are and what you do with their data. If an assistant can now read their booking or their invoice, your privacy information needs to cover that path, the purpose, and the categories of recipient. Do not hide the assistant behind a phrase such as “we use technology”. The ICO’s principle is fairness and transparency, not a template we can paste in for you.

The same care belongs in the wider design of the systems. Systems architecture is where a firm maps which system holds which fact. An MCP server should follow that map, not create a second, undocumented copy of the customer list.

MCP and A2A are different paths

MCP connects a model to tools and data. A2A lets one agent discover another and send it a task, using an Agent Card on a domain. A customer’s agent asking your business for a quote is A2A. Your assistant looking up the quote in your own diary is MCP. Many firms need one of them. Some need both. The comparison and the AI agent readiness service are the places to choose, rather than turning every protocol on because the names are current.

Data protection does not disappear because the caller is another agent. If the A2A skill returns personal data, the same principles apply to that response. Keep the public Agent Card free of customer records, and keep the MCP tools narrow.

Frequently asked questions

What can an MCP server see in a small business?

Only the tools, resources and prompts you expose. The protocol does not automatically open every system. A typical setup might offer a diary, a product list or a customer record, and only the fields that tool returns. If you do not connect a system, the assistant does not get it through MCP.

Does UK GDPR ban MCP servers?

No. The ICO's principles still apply when personal data is involved: a fair and lawful reason, a clear purpose, no more data than you need, accuracy, limits on how long you keep it, and appropriate security. Connecting an assistant is a design and governance choice, not a banned technology. This page is not a decision for your business.

Who is the controller if an assistant uses our CRM?

In principle, the organisation that decides why and how personal data is used is the controller. A supplier that processes that data only on your documented instructions may be a processor. If a supplier starts deciding its own purposes, it can become a controller for that processing. The ICO's guidance explains the terms. Get advice before you sign, and before you connect live customer data.
